## 1. どのデモを選ぶか

棚卸し（`inventory_skill.py`）の出力を、そのまま実演計画に対応させる。

| 棚卸しの出力 | 対応するデモ |
|---|---|
| 契約テスト・検証系スクリプト | 最初に実行する。前提が崩れていれば以降が無意味になる |
| `--dry-run` を持つスクリプト | dry-run → 本実行の順で見せる。影響範囲の事前提示は運用者への説得力になる |
| レポート・集計系スクリプト | 各段階の前後で実行し、効果を数値で残す |
| 段階/優先順位が定義されている | 定義順に実行し、各段階のコストと効果を計測する |
| テストファイル | 実アクセス不要の検証として最後に回す。全件パスを確認する |
| 「必ず」「禁止」の記述 | 対照実験の候補。3章を参照 |
| 数値の主張（○ms、○件） | 実測して突き合わせる。一致したことを明記する |

デモの数は 4〜8 本が適切である。1〜2 本では主張を網羅できず、10 本を超えると
どれが重要だったか伝わらなくなる。**最も価値のあるデモを 1 本明示する**とよい。

---

## 2. 規模の決め方

実演の目的は網羅ではなく実証である。規模は次の条件を満たす最小値にする。

- 段階間の差が数値として現れる（充填率が 0% → 100% と動く）
- 外部レート制限に当たらない（間隔 1500〜2000ms で数十件まで）
- 全体が 10 分程度で終わる

段階的な手法を検証する場合、**全件を埋めない**ことが逆に重要である。
「12/46 件だけ詳細を取得した」状態は、オンデマンド補完の対象が残っていることを
示せるため、パイプライン設計の意図がそのまま可視化される。

規模を絞ったことによる限界（レート制限が再現しなかった、バルク化の効果が見えない等）は
レポートの「運用上の補足」に正直に書く。

## 3. 主張の種類別・検証方法

### 「Xしないと壊れる」（禁止・義務の主張）

対照実験を組む。`ab_guard_probe.py` に以下を渡す。

- **setup**: 壊れる条件を意図的に作る（誤ったIDを紐付ける、不正な入力を混ぜる）
- **guarded**: スキルが規定する正しい実装で実行
- **unguarded**: 該当する機構だけを外した実装で実行
- **observe**: 状態を1行1レコードで出力するコマンド（差分比較に使う）
- **teardown**: 元に戻す

機構なし版は、正しい実装からガード部分のみを削除して作る。別物を書くと
「実装が違うから結果が違う」という反論を許してしまう。

判定は「機構ありで状態が変化せず、機構なしで変化する」の両方が成立して初めて成功。
機構なしでも壊れなかった場合は破壊条件の仕込みが弱い。

**この種の障害は例外を投げずに進行することが多い。** その性質をレポートで
明示する（「プログラムは一つも例外を投げず、ログにも異常は残らない」）。

### 「Yの方が安い」（コスト効率の主張）

推奨手法の実測コストと、非推奨手法の理論コストを並べる。非推奨手法は
実際に走らせる必要はない（走らせるとコストを無駄に消費する）。ただし
理論値であることを明記し、算出根拠を書く（「1件あたり3リクエスト × 46件」）。

### 「Zミリ秒で応答する」（性能の主張）

同一処理を状態を変えて複数回実行し、差を示す。キャッシュや充填状況で
分岐する処理なら「初回 / 2回目」の対比が最も分かりやすい。

### 「入力Wを正しく処理する」（パーサ・変換の主張）

境界的な入力が実データに含まれるように対象を選ぶ。たとえば性別判定の検証には
一般的な値だけでなく稀な値を含むレコードを対象に入れる。含まれなかった場合は
同梱の単体テストで補う。

## 4. 実データが使えない場合

外部サービスが停止している、認証情報が無い、課金が発生するなどで実データが
取得できないときは、次の順に代替する。

1. **同梱の単体テスト**を実行する。実HTMLやAPIレスポンスを模した固定文字列に対する
   テストであれば、パーサの正しさは実アクセスなしで示せる
2. **ローカルで再現できる部分だけ**を実演する（SQL処理、変換ロジック、バリデーション）
3. **取得できなかったことを明記**し、何が未検証かをレポートに残す

実データが取れないことを伏せて模擬データで代替し、それを実測値として提示するのは
避ける。数値の信頼性が失われ、レポート全体が無意味になる。

## 5. アンチパターン

| やりがちなこと | なぜ問題か | 代わりにすること |
|---|---|---|
| 成功ケースだけ並べる | 安全機構の価値が伝わらない | 対照実験で機構なし版の破綻を見せる |
| 「正常に動作しました」で締める | 何が検証されたか不明 | 前後の数値と実データを表で示す |
| 全件を処理して充填率100%にする | 段階設計の意図が消える | 意図的に一部を残し、次段階の対象を可視化する |
| 非推奨手法を実際に走らせる | コストの無駄。場合により相手に負荷 | 理論値として算出し根拠を書く |
| 後片付けをしない | 次の実演や本番データを汚す | teardown を必ず用意し、失敗時も実行する |
| 破壊実験を本番DBで行う | 復旧不能な事故 | サンドボックスに専用DBを作る |
| ログの生出力をレポートに全文貼る | 読めない | 判定に効く数行だけ引用し、全文は添付する |
| スキルの記述をそのまま要約する | 実演の意味がない | 実測値と突き合わせ、一致/不一致を述べる |
