# 実演レポートの構成

## 冒頭の免責（必須・省略不可）

フィクスチャで実演したレポートは、**本文の前に必ず出典を明示する**。これを省くと、読者が実在データの分析結果と誤認し、誤った経営判断や実装判断につながる。

```markdown
> **本レポートの位置づけ**
> 本文書は `<対象スキル名>` スキルの動作実演レポートである。分析対象は、
> 稼働中システムのDBに接続できなかったため、スキル付属の
> `<参照先スキーマ>` に完全準拠して構築した**検証用フィクスチャデータ**である。
> 実在の固有名詞・実測値は一切含まれていない。したがって本文中の数値は
> 「このスキルが何をどこまで検出できるか」を示すものであり、実在する
> 対象の分析結果ではない。実DBを接続すれば同一のワークフローが
> そのまま適用できる。
```

引用ブロックで囲み、タイトルより前に配置する。

## 全体構成

```markdown
# <対象スキル名> 実演レポート

**作成者**: Manus AI
**作成日**: YYYY年M月D日
**対象スキル**: `skill-name`
**検証データ**: N件 / 期間 / セグメント数

## エグゼクティブサマリー
（3〜5文。検出できた症状の数、最も重要な発見、スキル自体の問題の有無）

## 1. 実演の設計
（埋め込んだ症状と対応する判定基準の表。スキーマ準拠の明記）

## 2〜5. 分析軸ごとの結果
（対象スキルの分析軸に沿って章立て。各章に図を1枚以上）

## 6. スキル自体の検証で判明した問題と修正
（重大度順。再現手順とエラーメッセージ、修正コードを含む）

## 7. 根本原因と改善提案
（優先度つきの原因表 → 優先度順の改善提案）

## 8. 結論
（スキルの有効性の評価と、修正版使用の推奨）

## 添付ファイル
（ファイル名と内容の表）
```

## 各章の書き方

### 実演の設計

埋め込んだ症状と、それが対象スキルのどの判定基準に対応するかを表で示す。この対応関係が明示されていないと、「都合のよいデータを作っただけ」という疑いを招く。

| ケース | 埋め込んだ症状 | 対応する判定基準 |
|---|---|---|
| A | 週次で的中率が段階的に低下 | 直近1週間との比較による急落判定 |
| B | 主要スコアのみ、補正値は全てゼロ | 構成比 > 80% → 依存過多 |

### 分析軸ごとの結果

各章は「図 → 数値表 → 解釈」の順で構成する。図だけ、表だけでは読者が結論に到達できない。

解釈では、**数値が何を意味するかを一段掘る**。「的中率が6.9%だった」で止めず、「これは前週比 -10.9pt であり、同時に万馬券率が倍増しているため、精度低下と環境変化が同時進行している」まで書く。

母数の少ないセグメントには必ず注記を入れる。実演の中で「参考値の注記がないと誤読する」ことを指摘するなら、レポート自身がその作法を守っていなければ説得力がない。

### スキル自体の検証で判明した問題

これが実演レポートの最大の付加価値である。単に「動きました」で終わるレポートには価値がない。

重大度順に並べ、各問題について次の3点を書く。

1. **再現**: 該当コードの引用（ファイル名と行番号つき）と、実際のエラーメッセージ
2. **原因**: なぜそうなるのかの技術的説明
3. **修正**: 具体的なコード

```markdown
### 問題1：import パスの不備（致命的・現状では起動不能）

`scripts/analyze.mjs` の13行目は次のようになっている。

```js
import mysql from './node_modules/mysql2/promise.js';
```

ESM の相対パスは**スクリプトファイル自身の位置**を基準に解決される。
したがって指示どおりプロジェクトディレクトリで実行しても、Node は
スキルディレクトリ配下の `node_modules` を探し、次のエラーで停止する。

> Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/home/ubuntu/skills/.../scripts/node_modules/mysql2/promise.js'

修正は次の一行で足りる。

```js
import mysql from 'mysql2/promise';
```
```

軽微な問題は表にまとめて圧縮する。

### 根本原因と改善提案

原因を**層に分解**する。表層の症状と根本原因を混同しない。

| 優先度 | 根本原因 | 根拠となる実測値 | 影響 |
|---|---|---|---|
| 最高 | スコアが単一指標の単調変換でしかない | 構成比 99.77%、外れの100%が閾値以下 | 環境変化で構造的に崩壊 |
| — | 環境要因（対応不可） | 万馬券率69% | この日の外れは欠陥ではない |

**対応不可能な要因を明示的に分離する**ことが重要である。これを混ぜると、避けられない事象に対してアルゴリズムを合わせ込む過剰適合の提案になってしまう。

改善提案は箇条書きの羅列を避け、優先度ごとに段落で書く。各提案には「なぜその優先度なのか」の根拠（既存データで着手できる／データ蓄積待ち等）を添える。

## 図表の作り方

Python（matplotlib）で生成し、PNG に保存してから Markdown で参照する。日本語を含む場合はフォント設定を忘れない。

```python
plt.rcParams["font.family"] = "Noto Sans CJK JP"
plt.rcParams["axes.unicode_minus"] = False
```

推奨する4種の図は次のとおり。

| 図 | 内容 | 目的 |
|---|---|---|
| 1 | 時系列推移（棒＋折れ線の複合、判定ラベル付き） | 悪化のタイミングと環境変化の同時進行を示す |
| 2 | 構成比の横棒＋外れ分布のヒストグラム | 診断の根拠を2つ並べて示す |
| 3 | セグメント別の棒（全体平均線つき、色分け） | 弱点の所在を示す |
| 4 | 構成比の積み上げ推移 | 質的な変化を示す |

図には数値ラベルを直接描き込む。読者が図と表を往復しなくても要点が伝わる。判定結果（「大荒れ」等）は図中に注記ボックスで置くと、図単体で結論が読める。
