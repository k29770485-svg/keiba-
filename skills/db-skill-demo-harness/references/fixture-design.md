## 症状駆動設計

ランダムなデータを大量に作っても実演にはならない。**対象スキルが検出すると主張している症状を逆算して埋め込む**のが原則である。

手順は次のとおり。

1. 対象スキルの参照ドキュメント（判定基準・診断表・閾値表）を読む
2. そこに書かれた各パターンを1つずつ「ケース」として採用する
3. 各ケースに対し、判定基準を確実に超える（または下回る）パラメータを設定する
4. 健全な状態のケースも必ず1つ入れる — 比較対象がないと「低い」と言えない

対象スキルに閾値表がある場合、それが最良の設計図になる。例として、あるスキルの判定基準が次のようになっていたとする。

| 指標 | 通常 | やや荒れ | 大荒れ |
|---|---|---|---|
| 万馬券率 | <20% | 20-50% | >50% |
| 予想◎3着以内率 | >40% | 20-40% | <20% |

この場合、`通常`・`やや荒れ`・`大荒れ` の3プロファイルを作り、それぞれの区間の中央値付近を狙う。境界値ちょうどを狙うと乱数で判定が揺れるため避ける。

### 健全性チェックがある場合

「A の構成比 > 80% なら異常」のようなチェックがあるなら、**A のみに値を入れ他をゼロにする**モードを作る。これで構成比は 100% 近くになり、チェックが確実に発火する。逆に全要素へ値を入れた「改善後」モードも用意すると、改善提案の妥当性を示す材料になる。

## 生成コードの構造

再現性と調整可能性を両立させるため、次の構造を推奨する。

```python
random.seed(20260804)          # 必ず固定。再実行で同じ結果になる

SCHEDULE = [                   # 期間の設計を1箇所に集約
    ("2026-07-11", 12, "healthy"),
    ("2026-07-12", 36, "healthy"),
    ("2026-08-01", 36, "chaos"),
]

PROFILE = {                    # 症状をパラメータとして宣言
    "healthy": dict(hit_rate=0.30, in3=0.52, manba=0.17),
    "chaos":   dict(hit_rate=0.03, in3=0.14, manba=0.61),
}

SEGMENT_PENALTY = {            # セグメント別の弱点を係数で表現
    "会場A": 1.15, "会場B": 0.45,
}
```

`SCHEDULE` と `PROFILE` が分離していれば、検証で FAIL が出たときに確率を数値で調整するだけで再投入できる。生成ロジック本体を書き換える必要がない。

セグメント別の弱点は、基準確率に乗じる**係数**として実装する。こうすると「会場Bは的中率が低い」という症状と「全体の的中率」を独立に制御できる。

## 現実味を作る要素

実演レポートの説得力は、データが本物らしく見えるかに依存する。次の要素を入れると質が上がる。

**母数の非対称性** — 実運用データは日ごとの件数が揃っていない。平日12件・週末36件のように差をつけると、「日別比較では判断できない、週次集計が必要」という重要な論点が自然に浮かび上がる。この論点は対象スキルの注意事項に書かれていることが多く、それを実演で裏づけられる。

**右裾の長い分布** — 配当・金額・滞留時間などは対数正規に近い分布を持つ。一様乱数で作ると平均と中央値がほぼ一致してしまい、「平均値だけを見ると誤読する」という指摘ができなくなる。少数の極大値を意図的に混ぜる。

```python
if 荒れフラグ:
    payout = random.randint(10000, 480000)   # 万馬券帯
else:
    payout = random.randint(900, 9800)       # 通常帯
```

**部分実装のノイズ** — 「全レコードで bonus がゼロ」より「95%がゼロ、5%は値が入っている」のほうが現実に近い。完全にゼロだと「機能が存在しない」とも読めるが、部分的に値があると「実装途中で放置されている」という診断ができる。

```python
algo_mode = "partial" if random.random() < 0.12 else "odds_only"
```

**サンプル過少セグメント** — 母数10〜20件のセグメントを意図的に作る。ここで極端な率が出ることで、「母数下限の注記がないと誤読する」という監査ポイントを実証できる。

## 混同を避ける命名

実在の固有名詞は使わない。レポートを読んだ人が実在データと誤認するリスクを完全に排除する。

機械的な接頭辞と接尾辞の組み合わせで生成すると、明らかに架空であることが一目で分かる。

```python
PREFIX = ["デモ", "テスト", "サンプル", "フィクス", "ダミー", "ベンチ", "モック", "トライ"]
SUFFIX = ["エース", "ロード", "クイーン", "スター", "ブレイズ", "ウィング"]
name = random.choice(PREFIX) + random.choice(SUFFIX)
```

英語圏のデータなら `TestCorp Alpha`、`DemoUser 001` のような形式にする。

生成スクリプトの冒頭には、必ず以下の趣旨のコメントを入れる。

```python
"""
【重要】このデータは実際の記録ではなく、スキルの分析ワークフローを
検証するために設計された合成テストフィクスチャである。
実在の固有名詞は使用していない。
"""
```

## よくある失敗

**症状が出ていない** — 乱数の巡り合わせで狙った症状が消える。`verify_fixture.py` で必ず検算する。目視で「それらしい数字」を確認するだけでは見落とす。

**症状が強すぎる** — 的中率0%、万馬券率100%のような極端なデータは、分析の説得力を逆に損なう。「このデータは作り物だ」という印象が前面に出てしまい、スキルの検出能力を評価できない。判定基準を明確に超えつつ、実運用であり得る範囲に収める。

**健全なケースがない** — すべての開催日が異常だと、「低い」「急落した」という判断の基準線が存在しない。全体の3〜5割は健全なデータにする。

**JOINで行が落ちる** — 外部キーの設定を誤ると、JOIN後の件数が投入件数より少なくなり、分析結果が実際より小さく出る。`verify_fixture.py` の構造チェックで検出できる。

**日付フォーマットの不一致** — スキーマが `VARCHAR` で日付を持つ場合、`BETWEEN` 比較は文字列比較になる。`2026-7-1` のようなゼロ埋めなしの値を混ぜると範囲検索から漏れる。必ず `YYYY-MM-DD` で統一する。
