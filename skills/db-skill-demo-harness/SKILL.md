# DB依存スキルの実演・監査ハーネス

## いつ使うか

「このスキルをデモしてほしい」「動作を検証してほしい」と依頼されたが、対象スキルが稼働中システムのDBへの接続を前提としており、**実データにアクセスできない**場合に使う。

実データが利用可能なら、そのまま対象スキルを実行するのが常に最善である。このハーネスは代替手段であり、以下の判断を最初に行う。

1. 実DBに接続できるか確認する（環境変数 `DATABASE_URL`、プロジェクトディレクトリ、コネクタの有無）
2. 接続できない場合、**ユーザーに2つの方針を提示して選択を仰ぐ**
   - 方針A: 実DB/プロジェクトを添付してもらい実データで実演
   - 方針B: スキーマ準拠のフィクスチャで全ワークフローを実演
3. 方針Bが選ばれた場合、または「まず動きを見たい」という意図が明確な場合に本ハーネスを適用する

ユーザーに無断でフィクスチャデータを使い、それを実データのように提示することは絶対に避ける。

---

## ワークフロー

全体は6ステップで構成される。

1. 対象スキルの読解と静的監査（`audit_target_scripts.py`）
2. ローカルDB環境の構築（`setup_local_db.sh`）
3. スキーマ準拠のフィクスチャ設計・投入
4. フィクスチャの検算（`verify_fixture.py`）
5. 対象スキルの実行と深掘り分析・可視化
6. 実演レポートと修正版スクリプトの納品

### Step 1: 対象スキルの読解と静的監査

対象スキルの `SKILL.md`、`references/` 配下すべて、`scripts/` 配下すべてを読む。特に次の3点を抽出する。

- **スキーマ定義**: テーブル名、カラム名、型、JOIN関係、JSONカラムの内部構造
- **判定基準・閾値表**: フィクスチャ設計の設計図になる（最重要）
- **注意事項**: 母数差、単位、フラグの意味など。実演で検証すべき論点が書かれている

次に静的監査を実行する。実行不能な欠陥を先に把握しておけば、接続できずに時間を浪費する事故を防げる。

```bash
python3 /home/ubuntu/skills/db-skill-demo-harness/scripts/audit_target_scripts.py /home/ubuntu/skills/<target-skill>
```

CRITICAL/HIGH が出た場合、**対象スキル本体は書き換えない**。作業ディレクトリに修正版をコピーして使い、修正内容は成果物として納品する。スキル本体の改変を求められた場合は skill-creator の更新ワークフローに従う。

検出パターンの詳細は `scripts/audit_target_scripts.py` の `CHECKS` を参照。よく出る欠陥は次のとおり。

| 重大度 | 欠陥 | 症状 |
|---|---|---|
| CRITICAL | ESM相対パスでの `node_modules` 参照 | `ERR_MODULE_NOT_FOUND` で起動不能 |
| HIGH | SSL設定のハードコード | `HANDSHAKE_SSL_ERROR` で接続不能 |
| MEDIUM | ゼロ除算の未対策 | 0件期間で `NaN%` を出力 |
| MEDIUM | セグメント集計の母数下限なし | 少数サンプルの外れ値を誤読させる |

### Step 2: ローカルDB環境の構築

```bash
bash /home/ubuntu/skills/db-skill-demo-harness/scripts/setup_local_db.sh <db_name>
```

最終行に出力される `DATABASE_URL` と `DB_SSL=off` を export する。`mysql-server` はサンドボックスに未インストールのことが多く、`apt-get update` が必要になる。スクリプトが自動処理する。

Python から接続する場合は `sudo pip3 install mysql-connector-python`、Node から使う場合は作業ディレクトリで `npm init -y && npm install mysql2` を実行する。対象スクリプトがベアインポートを使うなら、**作業ディレクトリの `node_modules` から解決される**。

### Step 3: スキーマ準拠のフィクスチャ設計・投入

対象スキルのスキーマ定義を**カラム名・型まで完全に一致させて**DDLを書く。ここを崩すと対象スキルのSQLがそのまま通らず、実演の意味が失われる。

生成コードの設計指針、現実味の作り方、命名規則は `references/fixture-design.md` を読む。要点だけ先に挙げる。

- 対象スキルの判定基準を逆算し、各パターンを「ケース」として埋め込む
- 健全な状態のケースを必ず1つ入れる（比較対象がないと「低い」と言えない）
- 母数を日ごとに非対称にする（単純比較不可という論点が浮かび上がる）
- 金額等は右裾の長い分布にする（平均と中央値の乖離を作る）
- 実在の固有名詞は使わず、機械的な接頭辞＋接尾辞で命名する
- `random.seed()` を固定し、`SCHEDULE` と `PROFILE` をパラメータとして分離する

### Step 4: フィクスチャの検算

乱数の巡り合わせで狙った症状が消えることがある。症状の無いデータで対象スキルを走らせても実演にならないため、必ず検算する。

期待値を JSON で宣言し、次を実行する。

```bash
export DATABASE_URL="mysql://..."
python3 /home/ubuntu/skills/db-skill-demo-harness/scripts/verify_fixture.py --expectations expectations.json
```

JSON の書き方は `references/expectations-example.json` をテンプレートとして使う。`connection` でJOIN構造を宣言し、`assertions` に各ケースの検算SQLと期待値（`lt` / `gte` / `between` 等）を書く。FAIL が出たら `PROFILE` の確率値を調整して再投入する。

構造チェックでJOIN成立件数が投入件数を下回った場合、外部キーの設定に誤りがある。分析結果が実際より小さく出るため必ず修正する。

### Step 5: 対象スキルの実行と深掘り分析

まず**対象スキル付属のスクリプトをそのまま実行する**。ここで失敗する場合、その失敗自体が最も価値のある発見である。エラーメッセージを記録し、修正版で再実行する。

対象スキルが複数の分析軸を定義している場合、全軸を実行する。異なる期間・条件で複数回実行し、健全な期間と悪化した期間を比較する。

付属スクリプトが出力しない分析（週次集計、中央値、分布、セグメント別クロス集計）は補完的に自作する。ここで「付属スクリプトに何が足りないか」が具体的に見える。

可視化は matplotlib で行い、PNG に保存する。図の種類と構成は `references/report-structure.md` を参照。日本語を含む場合は次を設定する。

```python
plt.rcParams["font.family"] = "Noto Sans CJK JP"
plt.rcParams["axes.unicode_minus"] = False
```

### Step 6: 実演レポートと修正版の納品

レポートは**冒頭にフィクスチャであることの免責を必ず置く**。これを省くと読者が実データと誤認する。構成の詳細とテンプレートは `references/report-structure.md` を読む。

納品物は次を揃える。

| 種別 | 内容 |
|---|---|
| レポート | 実演結果・スキルの問題点・改善提案を含む Markdown |
| 修正版スクリプト | 監査で見つけた欠陥を修正したもの（修正内容をヘッダコメントに明記） |
| 図表 | PNG 形式 |
| 集計データ | CSV |
| 再現用資材 | DDL、フィクスチャ生成スクリプト、分析スクリプト |

再現用資材を含めることで、ユーザーが自分の環境で追試できる。

## 設計の勘所

**評価対象はデータではなくスキルである。** 分析結果の数値そのものに意味はない。「その症状をスキルが検出できたか」「検出結果が正しく解釈可能な形で出力されたか」が評価軸である。レポートも分析結果の羅列ではなく、スキルの検出能力の評価として書く。

**「動きました」で終わらせない。** 実演の最大の付加価値は、対象スキルの欠陥を発見して修正版を提供することにある。元事例では、付属スクリプトが import パスの不備で起動すらできず、また母数15件のセグメントを無警告で出力して誤読を招く状態だった。これらは実データで走らせても気づきにくく、フィクスチャで系統的に検証したからこそ発見できた。

**対応不可能な要因を分離する。** 環境要因による失敗と、アルゴリズムの欠陥による失敗を混同すると、避けられない事象に合わせ込む過剰適合の提案になる。フィクスチャに「構造的に対応不可能なケース」を意図的に含めておくと、この分離ができているかを検証できる。

**フィクスチャの出自を隠さない。** レポート冒頭の免責、生成スクリプトのヘッダコメント、架空であることが明白な命名、この3点で二重三重に担保する。

## 対象がMySQL以外の場合

`setup_local_db.sh` は MySQL/TiDB 系を前提としている。他のDBでは Step 2 のみ差し替える。

| DB | セットアップ | Python ドライバ |
|---|---|---|
| PostgreSQL | `sudo apt-get install -y postgresql` | `psycopg2-binary` |
| SQLite | インストール不要（ファイルベース） | 標準ライブラリ `sqlite3` |
| MongoDB | Docker 利用を推奨 | `pymongo` |

`verify_fixture.py` は MySQL 前提のため、他DBでは接続部分（`connect()`）を差し替える。SQL方言の差（`YEARWEEK`、`JSON_EXTRACT` 等）にも注意する。Step 1・3・4・5・6 の考え方はDB種別に依存しない。
