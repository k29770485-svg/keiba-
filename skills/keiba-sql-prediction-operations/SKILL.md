# SQL蓄積型競馬予想運用

## 目的

発走前に得られたデータだけから予想を生成し、後から確定した結果・払戻と結び付ける。**未来情報を推測・補完しない**。画面では、発走前予想、結果待ち、確定結果を混在させない。

最初に `references/data-contract.md` を読み、既存スキーマとの差分を確認する。APIまたは画面を追加する場合は `references/display-contract.md` も読む。レスポンス形は `templates/prediction-history-board-response.json` を参照する。

## 必須原則

1. 発走前入力は時刻付きスナップショットとして保存し、発走後のオッズ・着順・払戻を予想ロジックへ渡さない。
2. 予想生成は `race_id` とアルゴリズム版の組で一意に保存し、スコア内訳・欠損項目・穴馬判定・買い目を監査可能にする。
3. 確定結果がないレースは精算しない。払戻JSONが不正または不足ならチケットを `pending` のまま残す。
4. 日次回収率は精算済み原票から再構築する。既存集計への加算だけで済ませず、直近期間を削除してから再集計し、遅延訂正での二重計上を防ぐ。
5. UIは `display_state` と `display_label` をAPIから受け取る。画面側で「結果待ち」を「不的中」へ推測変換しない。
6. 回収率・的中率は確定済みチケットだけで計算する。投資額が0円の見送りは分母に含めない。

## 実装ワークフロー

### 1. 既存実装を調査する

次を特定する。

- レース、発走予定時刻、レース状態、出走馬、オッズ、結果、払戻の所在。
- 既存の予想スコア式、穴馬条件、買い目条件、投資単位。
- DB方言と外部キー、一意キー、既存インデックス。
- トップページのAPI・画面・定期実行の入口。

過去データが欠損している場合、無理に取得・推測して回収率を作らない。未来レースから新スキーマへ蓄積する運用を優先する。

### 2. SQLデータ契約を導入する

`references/data-contract.md` の表を基準に、少なくとも次を用意する。

| 区分 | 必須テーブル | 役割 |
| --- | --- | --- |
| 発走前入力 | `race_market_snapshots` | スナップショットと取得時刻を保存する。 |
| 予想 | `sql_prediction_runs`、`sql_prediction_scores` | 実行、全馬スコア、穴馬、欠損を保存する。 |
| 買い目・結果 | `sql_prediction_tickets`、`sql_race_settlements` | 購入推奨と確定払戻を保存する。 |
| 表示高速化 | `prediction_performance_daily` | 日別・アルゴリズム別・券種別の確定実績を保存する。 |

全DDLに `IF NOT EXISTS` を使うか、マイグレーション管理下で適用する。複合インデックスはクエリの `WHERE`、`JOIN`、`ORDER BY` を元に追加し、追加前後で実行計画を確認する。

### 3. 予想と買い目を保存する

1. SQLから、予測対象時刻より前の最新スナップショットだけを取る。
2. データ欠損は既定値で隠さず、`missing_fields_json` へ記録する。
3. 決定論的スコア、期待値、順位、穴馬フラグを全頭分保存する。
4. 買い目は選択キーを正規化し、`prediction_id + ticket_type + selection_key` を一意にする。
5. 期待値条件を満たさない場合は、チケットを作らず「見送り」として予想実行だけを保存する。

同一レースを複数ワーカーが処理しないよう、期限付きロックまたは一意制約とトランザクションを使う。

### 4. 確定結果を精算する

1. `race_status='finished'` かつ確定払戻があるレースだけを取る。
2. `pending` チケットごとに払戻キーを照合し、投資額に比例した払戻額・収支を計算する。
3. 全チケットが精算済みになった予想実行だけを `settled` に更新する。
4. 払戻が欠けるチケットは保留し、予想実行を確定済みにしない。

精算と日次集計は同一トランザクションで行うか、日次集計を冪等な再構築バッチにする。

### 5. 日次集計を更新する

`prediction_performance_daily` は、直近7日程度の半開区間 `[start_date, end_date)` を毎回再構築する。

1. 対象期間の集計行を削除する。
2. `settlement_status='settled'` の原票を精算日時・アルゴリズム版・券種で `INSERT ... SELECT` する。
3. 原票集計と日次表の投資額、払戻額、収支を照合する。

時刻列に `DATE()` をかけて絞り込まず、`settled_at >= :start_at AND settled_at < :end_at` を使い、索引の範囲走査を維持する。

### 6. ダッシュボードを実装する

APIは、次の3区分を**別クエリまたは別セクション**で返す。

| セクション | 条件 | 表示禁止事項 |
| --- | --- | --- |
| これからの予想 | `runs.status='generated'`、レースが発走前 | 回収率・確定収支を表示しない。 |
| 結果待ち | レース終了、払戻または精算が未確定 | 不的中と表示しない。 |
| 過去予想履歴・確定結果 | `runs.status='settled'`、精算済み | 推定値ではなく確定投資・払戻・収支を表示する。 |

APIに、予想・精算・日次集計それぞれの最終更新時刻と再取得間隔を含める。画面は初回ローディング、再取得中、初回失敗、前回成功データを保った再取得失敗、手動再試行を実装する。

### 7. 検証と運用開始

次を必ずテストする。

- 発走後の入力を予想対象から除外すること。
- 欠損値を作り出さず記録すること。
- 同じ精算を繰り返してもチケットが二重精算されないこと。
- 同じ日付範囲の日次集計を繰り返しても二重加算されないこと。
- 見送り、結果待ち、的中、不的中の表示状態が正しいこと。
- 回収率が `SUM(return) / SUM(stake) * 100` で計算され、未精算を含まないこと。
- APIの型検証、パラメータバインド、`EXPLAIN ANALYZE` による主要SQLの実行計画。

DB接続情報と運用ホストを受け取るまでは、DDL・コード・テストを用意しても実データへの書込みや常駐実行を開始しない。定期実行には、アプリのスケジューラまたは監視付き常駐ワーカーを使う。

## パフォーマンス判断

最初に、`runs` のアルゴリズム版・状態・レースID、`tickets` の精算状態・精算日時・予想ID、`scores` の予想ID・穴馬フラグ・期待値を対象に複合インデックスを検討する。

原票テーブルに外部キーがある場合、MySQL InnoDBのパーティショニングは直接適用しない。外部キーを持たない日次集計表が十分大きくなり、月次アーカイブが必要になってから、主キーに日付を含めた月次パーティションを検討する。

## 完了時の報告

変更ファイル、スキーマ適用順、定期実行コマンド、未接続の入力源、テスト結果、データ表示の区分を簡潔に報告する。回収率は過去実績であり、将来の的中や利益を保証しないことを明記する。
