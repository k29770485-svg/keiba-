# 競馬予想運用

## 適用範囲

公式または利用許諾のあるデータだけを用いて、競馬予想Webアプリを構築・改善する。スクレイピング可否、利用規約、取得頻度を先に確認する。未取得データを補完・創作しない。結果、払戻、回収率は確定データだけで計算する。

> 予想値・期待値・回収率は不確実性を明記し、的中や利益を保証する表現を避ける。

## 実行順序

### 1. 事実とデータ契約を確認する

1. 対象レースを **開催日・競馬場・レース番号** で特定する。外部識別子だけに依存しない。
2. レース名、発走時刻、距離、芝/ダート、馬場状態、結果確定状態をDBと許諾データで照合する。
3. 距離・コース・レース名のいずれかが不一致なら、スコアリングや穴馬統計に近似条件を流用しない。正規値が得られる場合だけ自動補正し、画面で補正内容を表示する。
4. テーブルや列が不足していれば、スキーマを先に更新して非破壊SQLを適用する。INSERT/UPDATE後は必ずSELECTで確認する。

詳細な推奨データ契約は `references/data-contracts.md` を読む。

### 2. 公式データを取り込む

1. APIがWebアプリから利用できない場合、公式CSV/JSONのアップロード方式を優先する。認証情報をクライアントへ埋め込まない。
2. 取込時はファイル形式、raceId、馬番、オッズ値、取込時刻を検証する。
3. 取込監査ログを保存し、オッズ履歴を時系列で追加する。上書きだけで履歴を失わない。
4. 発走前の高頻度更新が必要なときは、対象を発走時刻で絞る。スケジュール実装前に `automation-and-scheduling` と `webdev-periodic-updates` を読む。永続環境が必要なら `persistent-computing` も読む。

### 3. 予想スコアを生成する

1. レース条件検証済みの出馬表だけを入力にする。
2. スコア内訳は、入力欠損による0点と実際の0点を区別する。前者は「データなし」と表示する。
3. 勝率はレース内のAIスコアを正規化した**推定勝率**として扱う。期待値は推定勝率とオッズから算出し、推定値であることを明示する。
4. 保存済み構造化予想を利用する場合、対象レース・出走馬と照合し、重複生成をロックで防ぐ。生成失敗時は決定論的スコアへフォールバックする。

### 4. 穴馬と買い目を整合させる

1. 穴馬候補TOP5を抽出したら、三連単の2・3着候補、三連複、ワイドの相手に必ず反映する。
2. 本線と保険を併存させる場合、対象馬集合と役割の違いを明示し、重複組合せを除外する。原則は本線中心のフォーメーションにする。
3. 人気軸は1着固定・相手を絞り、三連単をおおむね30点に抑える。穴軸は1〜2頭を1着候補とし、全券種合計で60点以内を上限にする。
4. 買い目文字列だけでなく、券種別点数、総点数、1点単位の想定投資額を保存する。過去データの点数を推測してはいけない。

### 5. カレンダーと結果画面を状態連動させる

1. 発走前は「予想する」、結果確定済みは「結果を見る」、発走後かつ未確定は「結果待ち」を出す。
2. 日付のみで過去・未来を判定しない。JSTの発走時刻と結果確定フラグを使用する。
3. 結果待ちが存在するときだけ短い間隔で再取得する。結果が確定したら自動更新を停止する。

### 6. 成績を分析する

1. 確定予想だけを対象に、投資額、払戻額、収支、回収率、的中率を集計する。
2. 総点数帯は `1–15 / 16–30 / 31–45 / 46–60 / 61+` を基本にし、回収率100%の参照線を表示する。
3. 点数未記録の旧履歴は「集計対象なし」として件数を示す。仮の点数や払戻を生成しない。

## よくある失敗と対策

| 失敗 | 対策 |
|---|---|
| 距離誤認で別コース統計を使用 | 正規レース照合に失敗したら分析を止め、近似距離を流用しない。 |
| 穴馬を検出したのに買い目から除外 | TOP5を候補集合へ固定してからフォーメーションを生成する。 |
| BOXと本線の重複で点数過多 | 券種別の組合せを正規化し、重複を除外してから合計点数を算出する。 |
| 当日レースが一律で結果扱い | 発走時刻と結果確定フラグで状態を判定する。 |
| 旧予想の点数を推測して分析 | 未記録として除外し、将来分から明示的に保存する。 |
